# Ansible Lab Automation

This document describes how ctlabs generates and runs Ansible playbooks from lab topology definitions. The system eliminates hardcoded per-lab playbooks by deriving everything from three profile files and the lab's own YAML.

---

## 1. Overview

Lab automation runs in four phases:

| Phase | What happens                                 |
|-------|----------------------------------------------|
| 1     | Create containers / VMs                      |
| 2     | Create network links                         |
| 3     | Write local facts to each host (`setup.yml`) |
| 4     | Run Ansible roles (`ctlabs.yml`)             |

Phases 3 and 4 use playbooks that are **generated by `lab.rb`** before Ansible is invoked. They are gitignored and must not be edited by hand.

---

## 2. Key Files

| File                                                      | Purpose                                                                                   |
|-----------------------------------------------------------|-------------------------------------------------------------------------------------------|
| `ctlabs/automation/lab/play_profiles.yml`                 | Maps profile names to roles, tags, and canonical host lists (lab scope)                   |
| `ctlabs/automation/lab/setup_profiles.yml`                | Default fact config per profile, merged with per-lab overrides (lab scope)                |
| `ctlabs/automation/ctl/*.yml`                             | The controller's own copies — two independent configs, same code                          |
| `ctlabs-ansible/playbooks/up.yml`                         | Waits for all nodes to be reachable (imported by generated `ctlabs.yml`)                  |
| `ctlabs-ansible/playbooks/setup.yml.tpl`                  | **Template** — hand-edited; decides the phase 3 facts_dir play and which hosts it touches |
| `ctlabs-ansible/playbooks/setup.yml`                      | Generated from the `.tpl` — writes local facts to hosts (phase 3)                         |
| `ctlabs-ansible/playbooks/setup_ctl.yml.tpl`              | **Template** for Controller→Ansible phase 3 (scoped to `controller`, not `all:!rhosts`)   |
| `ctlabs-ansible/playbooks/setup_ctl.yml`                  | Generated from the `.tpl` — controller's phase 3 playbook                                 |
| `ctlabs-ansible/playbooks/ctlabs.yml.tpl`                 | **Template** — hand-edited; decides what the generated `ctlabs.yml` imports/contains      |
| `ctlabs-ansible/playbooks/ctlabs.yml`                     | Generated from the `.tpl` — runs roles (phase 4)                                          |
| `ctlabs-ansible/playbooks/main.yml.tpl`                   | **Template** for Controller→Ansible (separate config, same code)                          |
| `ctlabs-ansible/playbooks/main.yml`                       | Generated from `main.yml.tpl` — controller's phase 4 playbook                             |
| `playbooks/.play_setup_lab.json` / `.play_setup_ctl.json` | Generated — per-host fact config passed to Ansible via `-e @` (scope-suffixed)            |

## 3. Naming Convention

Three names are involved; they are related, but not interchangeable:

- **profile key** — the entry name in `play_profiles.yml` (e.g. `rke2-server`).
  It is also an implicit tag and the settings key of last resort.
- **alias tags** — optional extra `tags:` on that entry, shared by related
  profiles (`rke2` on rke2-server / rke2-control / rke2-worker) so one lab tag
  activates the whole family.
- **settings key** — the lookup key in `setup_profiles.yml`; by convention the
  same as the profile key.

Per play profile, `build_play_setup` resolves two separate things:

1. **activation** — is any of (alias tags + profile key) present in
   `play.tags`?
2. **settings** — the first alias tag that is in `play.tags` *and* exists in
   `setup_profiles.yml`; otherwise the profile key itself if it exists there.

Explicit alias matches win over the name: lab tag `rke2` → settings `rke2`,
lab tag `rke2-server` → settings `rke2-server`. With only per-role settings
keys, `play.tags: [rke2]` is enough for the whole family.

An alias does not point at arbitrary settings — it finds the settings **of the
same name**. `play.setup` keys always name a settings key directly (per-lab
overrides merge on top of it).

Example profile keys: `bind`, `smbadc`, `rke2-server`, `claude`.

## 4. play_profiles.yml

Defines which Ansible role to run, which tags activate it, and which hosts it targets.

### Simple entry

```yaml
bind:
  role : ctlabs_bind
  tags : [bind]
  hosts: [ns1, ns2]
```

- `role` — Ansible role name under `ctlabs-ansible/roles/`
- `tags` — must match the lab's `play.tags` for this profile to be included
- `hosts` — canonical host list; filtered against nodes that actually exist in the lab

`hosts` may also be `all` to target every node (excluding `rhosts`).

### Sequential plays (separate profiles, file order)

When a role must run on some hosts before others (e.g. server before agents),
define **one profile per stage** and give them a shared activation tag. Plays
are emitted in **file order**, so the profile listed first runs first:

```yaml
k3s-server:
  role : ctlabs_k3s
  tags : [k3s, k3s-server]
  hosts: [k3s1]

k3s-control:
  role : ctlabs_k3s
  tags : [k3s, k3s-control]
  hosts: [k3s2, k3s3]

k3s-worker:
  role : ctlabs_k3s
  tags : [k3s, k3s-worker]
  hosts: [k3s4]
```

- Lab tag `k3s` activates all three; each stage also carries its own tag, so
  a lab can target one stage (`play.tags: [k3s-server]`) — provided
  `setup_profiles.yml` has facts for it (a tag that is also a setup key, or
  the stage's own name as the fallback).
- Each profile produces its own play in `ctlabs.yml` **and** its own facts
  play in `setup.yml` — there is no grouped `hosts:` form anymore.
- The old grouped syntax (`hosts: [{group: [...], tags: [...]}]`) and grouped
  per-lab `play.setup.<profile>.hosts` overrides are **removed**. Add or
  reorder stages by editing `play_profiles.yml`, not the lab file.

Current staged roles: `smbadc-master/slave`, `k3s-server/control/worker`,
`rke2-server/control/worker`, `k8s-server/control/worker`.

## 5. setup_profiles.yml

Default fact config per profile. Values are deep-merged with per-lab `play.setup` overrides.

```yaml
profiles:

  bind:
    role: bind
    ns1:
      type  : master
      zones :
        - name: ctlabs.internal
      slaves: [192.168.20.11]
    ns2:
      type   : slave
      zones  :
        - name: ctlabs.internal
      masters: [192.168.10.11]
```

- Top-level keys under the profile name are per-host config (keyed by hostname)
- Some profiles have top-level (non-host) config — e.g. `prometheus` has a `prometheus:` key that applies globally
- **Lists are united, not replaced** — a per-host (or per-lab) list adds to the
  defaults list: `(defaults + additions).uniq`, defaults first, order
  preserved. To change an item for everyone, edit the defaults; repeating a
  default item per host deduplicates instead of doubling it.
- **YAML anchors/aliases are supported** (`YAML.load_file` resolves `*alias`
  and the `<<` merge key) — but `<<` merges maps only, and list anchors still
  require every host to enumerate the shared items. Prefer the list-union
  above for defaults + per-host additions.

## 6. Lab YAML — play.setup

The `ansible` controller node in the lab YAML declares which roles run and any per-lab overrides:

```yaml
nodes:
  - name: ansible
    play:
      book: ctlabs.yml
      tags: [up, setup, ca, bind, k3s]
      setup:
        ca:
          domain: net03.ctlabs.internal
        bind:
          ns1:
            slaves: [10.0.3.11]
          ns2:
            masters: [10.0.3.10]
```

### play.tags

Controls which play profiles are included. Only profiles whose `tags` intersect with `play.tags` are emitted into the generated playbooks.

`up` and `setup` are always required — `up` waits for connectivity, `setup` writes facts.

### play.setup

Per-lab overrides merged on top of `setup_profiles.yml` defaults. Structure:

```yaml
setup:
  <profile_name>:
    <hostname>:
      key: value      # per-host override
    key: value        # global override (applies to all hosts via _role_facts fallback)
```

#### Global vs per-host config

In `facts.json.j2` templates, config is looked up in this order:

1. `ctlabs_role_facts` — per-host facts passed via `play_setup[profile][hostname]`
2. `play_setup[profile]` — top-level keys in the profile's `play.setup` entry
3. Hard-coded default (e.g. `CTLABS_DOMAIN`)

This means setting a value at the top level of `play.setup.<profile>` applies it to all hosts that don't have a per-host override.

#### hosts override

`play.setup.<profile>.hosts` overrides which hosts receive facts AND which hosts the role runs on.

Simple list or `all`:

```yaml
setup:
  ca:
    hosts: all          # run ca on every node
    domain: net03.ctlabs.internal
```

`hosts` must be a simple list or a string (`all`, a group name) — it cannot
change play order or grouping. Sequential stages are **separate play profiles
in `play_profiles.yml`** (see §4); edit that file to add or reorder stages:

```yaml
setup:
  k3s-server:
    hosts: [k3s1]       # narrow which hosts get this stage's facts + role run
```

#### Base profile always auto-loaded

When a `play.setup` entry exists for a profile, `lab.rb` always loads the matching `setup_profiles.yml` entry as the base first, then deep-merges the lab overrides on top. This means you only need to specify what differs from the defaults:

```yaml
setup:
  k3s:
    k3s2:
      role: worker    # overrides default 'control' for k3s2; all other k3s2 keys come from setup_profiles
```

A named `profile:` key overrides which profile is used as the base:

```yaml
setup:
  claude:
    profile: claude_openrouter   # use claude_openrouter profile as base instead of claude
```

#### Omitting play.setup for a profile

If a profile tag is in `play.tags` but has no entry in `play.setup`, `lab.rb` automatically loads the `setup_profiles.yml` defaults. No explicit `play.setup` entry is needed for profiles that use defaults unchanged.

#### profile key

A `play.setup` entry may reference a named profile from `setup_profiles.yml` as a base:

```yaml
setup:
  claude:
    profile: claude_openrouter
    ansible:
      provider:
        api_key_env: OPENROUTER_API_KEY
```

#### Per-host profiles

A per-host entry can specify its own `profile:` to use a different base from `setup_profiles.yml`. This is useful when multiple hosts need the same role but with different default configurations:

```yaml
setup:
  claude:
    hosts: [ansible, h1]
    ansible:
      profile: claude_openrouter
    h1:
      profile: claude_anthropic
      provider:
        api_key_env: MY_ANTHROPIC_KEY
```

Each host's resolution order is: **named host profile → shared role config (from `hosts` and top-level keys) → per-host overrides**. The per-host `profile:` is consumed during baking and does not appear in the final `.play_setup.json`.

## 7. Lab YAML — `${...}` placeholder expansion

Lab YAML values may reference other parts of the same file. Expansion happens in `lib/lab.rb` (`Lab.expand_placeholders`) on the raw text at load time, *before* the config is parsed into nodes.

| Placeholder                        | Resolves to                                          |
|------------------------------------|------------------------------------------------------|
| `${ctlabs_host}`                   | The lab server's public IP (legacy form)             |
| `${node:<name>}`                   | A node's address                                     |
| `${node:<name>:<attr>}`            | One attribute of a node (dotted paths allowed)       |
| `${node:<name>:<attr>:<idx>}`      | Index into a list-valued attribute (default `0`)     |

Attribute lookup, in order:

1. `nics.<attr>` — e.g. `${node:gcp-gw:nics.eth0}` → `35.200.10.7` (`nics.eth0.ip` style sub-keys work)
2. a top-level key — e.g. `${node:natgw:ipv4}` → `192.168.15.1`
3. `terraform.<attr>` — e.g. `${node:gcp-gw:terraform.work_dir}` → `cloud02`

With no `<attr>`, "a node's address" means the most useful single value: `nics.eth0`, else `nics.eth1`, else `nics.tun0`, else `nics.wg0`, else top-level `ipv4`, else `gw`. CIDR suffixes are always stripped — an endpoint never wants a prefix length.

### Why: configurable tunnel endpoints

A cloud gateway's public IP is not known until Terraform applies. The IP harvest (`Automation#run_terraform`) writes `nics.eth0 = <public>/32` back into the lab YAML; a placeholder is how that value reaches a *different* node's config:

```yaml
openvpn:
  ro1:
    type  : client
    remote: "${node:gcp-gw:nics.eth0}"   # -> the gateway's public IP
```

Either endpoint can be moved by editing one line — point `remote:` at another node/attribute, or swap which side is `server`. Nothing in Ruby hard-codes "the gateway is the server"; that lives entirely in `play.setup`.

### Failure behaviour

Unknown or unresolvable placeholders are left **verbatim** and logged as a warning — never silently blanked. A tunnel with a literal `${node:...}` in its `remote` fails visibly, whereas an empty `remote` is much harder to diagnose.

YAML comments are never expanded and never warn (prose documenting a placeholder is left alone).

## 8. Local Facts

Facts are written to `/etc/ansible/facts.d/<role>.fact` on each host and are accessible in playbooks as `ctg_facts.<role>.*`.

Example — reading bind facts:

```yaml
ctg_facts.ctlabs_bind.type     # 'master' or 'slave'
ctg_facts.ctlabs_bind.zones    # list of zone objects
ctg_facts.ctlabs_bind.slaves   # list of slave IPs (master only)
ctg_facts.ctlabs_bind.masters  # list of master IPs (slave only)
```

Facts are written by `include_role: tasks_from: facts.yml` in the generated `setup.yml`. Each role that supports facts has:

- `tasks/facts.yml` — writes the fact file using the template
- `templates/facts.json.j2` — Jinja2 template rendering JSON

A role without `tasks/facts.yml` is silently skipped in `setup.yml` generation.

---

## 9. Secrets

API keys and passwords must **never** appear in lab YAML or profile files. Always use environment variable lookups in `facts.json.j2`:

```jinja2
"api_key": "{{ lookup('env', 'ANTHROPIC_API_KEY') }}"
```

## 10. Generated Playbook Structure

### setup.yml (phase 3)

Everything above the per-profile facts plays comes from `setup.yml.tpl`
(`setup_ctl.yml.tpl` for Controller→Ansible), which you edit directly. The
controller's is scoped to the `controller` inventory group rather than
`all:!rhosts` — ctl-sw0/ctl-ro0 have no SSH keys, so `Gathering Facts` there
fails UNREACHABLE (Ansible exits status 4).

```yaml
- name : ctlabs.playbooks.setup
  hosts: all:!rhosts
  tags : setup
  tasks:
    - name: ctlabs.playbooks.setup.facts_dir
      file: { path: "{{ ctg_facts_dir }}", state: directory }

- name : ctlabs.playbooks.setup.bind
  hosts: ns1,ns2
  tags : setup
  tasks:
    - name: ctlabs.playbooks.setup.bind.facts
      include_role:
        name      : ctlabs_bind
        tasks_from: facts.yml
      vars:
        ctlabs_role_facts: "{{ (play_setup['bind'] | default({}))[inventory_hostname] | default({}) }}"
```

### ctlabs.yml (phase 4)

Everything above the role plays comes from `ctlabs.yml.tpl`, which you edit
directly — there is no conditional logic choosing imports. On each run the
generator only replaces the `{{PLAYS}}` line with the role plays selected by
`play.tags`. Controller→Ansible uses its own `main.yml.tpl` (no `up.yml` /
`setup_ctl.yml` import — ctl-sw0/ctl-ro0 have no SSH keys yet).

`ctlabs.yml.tpl`:

```yaml
- import_playbook: up.yml
- import_playbook: setup.yml

{{PLAYS}}
```

Generated `ctlabs.yml`:

```yaml
- import_playbook: up.yml
- import_playbook: setup.yml

- name : ctlabs.playbooks.ctlabs.bind
  hosts: ns1,ns2
  tags : [bind]
  roles:
    - roles/ctlabs_bind

- name : ctlabs.playbooks.ctlabs.k3s
  hosts: k3s1
  tags : [k3s-server, k3s]
  roles:
    - roles/ctlabs_k3s

- name : ctlabs.playbooks.ctlabs.k3s
  hosts: k3s2,k3s3
  tags : [k3s-control, k3s]
  roles:
    - roles/ctlabs_k3s

- name : ctlabs.playbooks.ctlabs.k3s
  hosts: k3s4
  tags : [k3s-worker, k3s]
  roles:
    - roles/ctlabs_k3s
```

## 11. Adding a New Role

1. Create the Ansible role under `ctlabs-ansible/roles/ctlabs_<name>/`
2. Add `tasks/facts.yml` and `templates/facts.json.j2` if the role needs local facts
3. Add an entry to `play_profiles.yml` with role, tags, and canonical hosts
4. Add an entry to `setup_profiles.yml` with sensible defaults (if the role has facts)
5. Add the tag to the relevant lab's `play.tags`
6. Add a `play.setup.<name>` entry in the lab YAML only if the lab needs non-default config
