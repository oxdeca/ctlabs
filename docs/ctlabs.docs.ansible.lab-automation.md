# Ansible Lab Automation

This document describes how ctlabs generates and runs Ansible playbooks from lab topology definitions. The system eliminates hardcoded per-lab playbooks by deriving everything from three profile files and the lab's own YAML.

---

## 1. Overview

Lab automation runs in four phases:

| Phase | What happens                                 |
|-------|----------------------------------------------|
| 1     | Create containers / VMs                      |
| 2     | Create network links                         |
| 3     | Write local facts to each host (`setup.yml`) |
| 4     | Run Ansible roles (`ctlabs.yml`)             |

Phases 3 and 4 use playbooks that are **generated by `lab.rb`** before Ansible is invoked. They are gitignored and must not be edited by hand.

---

## 2. Key Files

| File                                  | Purpose                                                                  |
|---------------------------------------|--------------------------------------------------------------------------|
| `ctlabs/labs/role_profiles.yml`       | Maps profile names to roles, tags, and canonical host lists              |
| `ctlabs/labs/setup_profiles.yml`      | Default fact config per profile, merged with per-lab overrides           |
| `ctlabs-ansible/playbooks/up.yml`     | Waits for all nodes to be reachable (imported by generated `ctlabs.yml`) |
| `ctlabs-ansible/playbooks/setup.yml`  | Generated — writes local facts to hosts (phase 3)                        |
| `ctlabs-ansible/playbooks/ctlabs.yml` | Generated — runs roles (phase 4)                                         |
| `.play_setup.json`                    | Generated — per-host fact config passed to Ansible via `-e @`            |

---

## 3. Naming Convention

One name is used everywhere for a given role:

```
role_profiles key  =  setup_profiles key  =  ansible tag  =  play.setup key
```

Example: `bind`, `smbadc`, `k3s`, `claude_code`.

This means a lab's `play.tags` list, `play.setup` keys, and `role_profiles.yml` keys all use the same identifier.

---

## 4. role_profiles.yml

Defines which Ansible role to run, which tags activate it, and which hosts it targets.

### Simple entry

```yaml
bind:
  role : ctlabs_bind
  tags : [bind]
  hosts: [ns1, ns2]
```

- `role`  — Ansible role name under `ctlabs-ansible/roles/`
- `tags`  — must match the lab's `play.tags` for this profile to be included
- `hosts` — canonical host list; filtered against nodes that actually exist in the lab

`hosts` may also be `all` to target every node (excluding `rhosts`).

### Grouped hosts (sequential plays)

When a role must run on some hosts before others (e.g. server before agents), `hosts` becomes a list of groups:

```yaml
k3s:
  role : ctlabs_k3s
  tags : [k3s]
  hosts:
    - group: [k3s1]
      tags : [k3s-server]
    - group: [k3s2, k3s3, k3s4]
      tags : [k3s-agent]
```

- Each group becomes a **separate sequential play** in the generated `ctlabs.yml`
- Group `tags` are extra tags — the top-level role tag (`k3s`) is **always appended automatically**
- Generated plays will have `tags: [k3s-server, k3s]` and `tags: [k3s-agent, k3s]`
- Facts are still written to all group members in a single `setup.yml` play

Examples of Roles using grouped hosts: `smbadc`, `k3s`, `rke2`.

## 5. setup_profiles.yml

Default fact config per profile. Values are deep-merged with per-lab `play.setup` overrides.

```yaml
profiles:

  bind:
    role: bind
    ns1:
      type  : master
      zones :
        - name: ctlabs.internal
      slaves: [192.168.20.11]
    ns2:
      type   : slave
      zones  :
        - name: ctlabs.internal
      masters: [192.168.10.11]
```

- Top-level keys under the profile name are per-host config (keyed by hostname)
- Some profiles have top-level (non-host) config — e.g. `prometheus` has a `prometheus:` key that applies globally
- **Lists are replaced, not merged** — if a lab overrides `zones`, it must supply the full list
- **No YAML anchors** — Ruby's YAML parser does not support them; duplicate values explicitly

## 6. Lab YAML — play.setup

The `ansible` controller node in the lab YAML declares which roles run and any per-lab overrides:

```yaml
nodes:
  - name: ansible
    play:
      book: ctlabs.yml
      tags: [up, setup, ca, bind, k3s]
      setup:
        ca:
          domain: net03.ctlabs.internal
        bind:
          ns1:
            slaves: [10.0.3.11]
          ns2:
            masters: [10.0.3.10]
```

### play.tags

Controls which role profiles are included. Only profiles whose `tags` intersect with `play.tags` are emitted into the generated playbooks.

`up` and `setup` are always required — `up` waits for connectivity, `setup` writes facts.

### play.setup

Per-lab overrides merged on top of `setup_profiles.yml` defaults. Structure:

```yaml
setup:
  <profile_name>:
    <hostname>:
      key: value      # per-host override
    key: value        # global override (applies to all hosts via _role_facts fallback)
```

#### Global vs per-host config

In `facts.json.j2` templates, config is looked up in this order:

1. `ctlabs_role_facts` — per-host facts passed via `play_setup[profile][hostname]`
2. `play_setup[profile]` — top-level keys in the profile's `play.setup` entry
3. Hard-coded default (e.g. `CTLABS_DOMAIN`)

This means setting a value at the top level of `play.setup.<profile>` applies it to all hosts that don't have a per-host override.

#### hosts override

`play.setup.<profile>.hosts` overrides which hosts receive facts AND which hosts the role runs on:

```yaml
setup:
  ca:
    hosts: all          # run ca on every node
    domain: net03.ctlabs.internal
```

#### Omitting play.setup for a profile

If a profile tag is in `play.tags` but has no entry in `play.setup`, `lab.rb` automatically loads the `setup_profiles.yml` defaults. No explicit `play.setup` entry is needed for profiles that use defaults unchanged.

#### profile key

A `play.setup` entry may reference a named profile from `setup_profiles.yml` as a base:

```yaml
setup:
  claude_code:
    profile: claude_openrouter
    ansible:
      provider:
        api_key_env: OPENROUTER_API_KEY
```

## 7. Local Facts

Facts are written to `/etc/ansible/facts.d/<role>.fact` on each host and are accessible in playbooks as `ctg_facts.<role>.*`.

Example — reading bind facts:

```yaml
ctg_facts.ctlabs_bind.type     # 'master' or 'slave'
ctg_facts.ctlabs_bind.zones    # list of zone objects
ctg_facts.ctlabs_bind.slaves   # list of slave IPs (master only)
ctg_facts.ctlabs_bind.masters  # list of master IPs (slave only)
```

Facts are written by `include_role: tasks_from: facts.yml` in the generated `setup.yml`. Each role that supports facts has:

- `tasks/facts.yml` — writes the fact file using the template
- `templates/facts.json.j2` — Jinja2 template rendering JSON

A role without `tasks/facts.yml` is silently skipped in `setup.yml` generation.

---

## 8. Secrets

API keys and passwords must **never** appear in lab YAML or profile files. Always use environment variable lookups in `facts.json.j2`:

```jinja2
"api_key": "{{ lookup('env', 'ANTHROPIC_API_KEY') }}"
```

## 9. Generated Playbook Structure

### setup.yml (phase 3)

```yaml
- name : ctlabs.playbooks.setup
  hosts: all:!rhosts
  tags : setup
  tasks:
    - name: ctlabs.playbooks.setup.facts_dir
      file: { path: "{{ ctg_facts_dir }}", state: directory }

- name : ctlabs.playbooks.setup.bind
  hosts: ns1,ns2
  tags : setup
  tasks:
    - name: ctlabs.playbooks.setup.bind.facts
      include_role:
        name      : ctlabs_bind
        tasks_from: facts.yml
      vars:
        ctlabs_role_facts: "{{ (play_setup['bind'] | default({}))[inventory_hostname] | default({}) }}"
```

### ctlabs.yml (phase 4)

```yaml
- import_playbook: up.yml
- import_playbook: setup.yml

- name : ctlabs.playbooks.ctlabs.bind
  hosts: ns1,ns2
  tags : [bind]
  roles:
    - roles/ctlabs_bind

- name : ctlabs.playbooks.ctlabs.k3s
  hosts: k3s1
  tags : [k3s-server, k3s]
  roles:
    - roles/ctlabs_k3s

- name : ctlabs.playbooks.ctlabs.k3s
  hosts: k3s2,k3s3,k3s4
  tags : [k3s-agent, k3s]
  roles:
    - roles/ctlabs_k3s
```

## 10. Adding a New Role

1. Create the Ansible role under `ctlabs-ansible/roles/ctlabs_<name>/`
2. Add `tasks/facts.yml` and `templates/facts.json.j2` if the role needs local facts
3. Add an entry to `role_profiles.yml` with role, tags, and canonical hosts
4. Add an entry to `setup_profiles.yml` with sensible defaults (if the role has facts)
5. Add the tag to the relevant lab's `play.tags`
6. Add a `play.setup.<name>` entry in the lab YAML only if the lab needs non-default config
